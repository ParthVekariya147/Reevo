# Reevo Performance Audit Report — Phase 1

> Generated by static analysis. All file:line references are exact. Impact ratings assume production-scale data (thousands of businesses, millions of scans/events).

---

## LEGEND
- **Impact: HIGH** — causes measurable latency / memory pressure today or at ~1k+ businesses
- **Impact: MED** — degrades at scale or in edge cases
- **Impact: LOW** — minor or only relevant under specific conditions

## 1. API Routes

### [HIGH] `src/app/api/admin/abuse/route.ts:14-17` — Unbounded table fetch, client-side aggregation
```
const { data: recentScans } = await db
  .from('qr_scans')
  .select('qr_id')
  .gte('scanned_at', since);
```
Fetches **every `qr_id` from `qr_scans` for the last 7 days with no `.limit()`**. At 10k scans/day × 7 days = 70k+ rows streamed from Supabase into Node.js memory just to do a JS-side GROUP BY. Node then counts them in a loop.
- **Proposed fix:** Replace with an RPC: `SELECT qr_id, COUNT(*) FROM qr_scans WHERE scanned_at >= $since GROUP BY qr_id HAVING COUNT(*) > 100`. No rows transit the wire.

### [HIGH] `src/app/api/admin/stats/route.ts:29-54` — 16 separate COUNT queries, no caching
```
const [...] = await Promise.all([
  db.from('businesses').select('id', { count: 'exact', head: true }),      // line 30
  db.from('businesses').select('id', { count: 'exact', head: true })...,   // line 31
  db.from('subscriptions')...  // × 4 queries
  db.from('qr_scans')...       // × 2 queries
  db.from('generated_reviews')... // × 2 queries
  db.from('analytics_events')... // × 4 queries
]);
// Then ANOTHER 2 sequential awaits: lines 51–54
```
Every admin dashboard load fires **16 round-trips to Postgres**. `{ count: 'exact' }` on `analytics_events` (can have millions of rows) triggers a full `COUNT(*)`. No `Cache-Control` header on this route — every page refresh re-runs all 16.
- **Proposed fix:** Consolidate into 1–2 RPCs. Add `Cache-Control: s-maxage=30, stale-while-revalidate=60` response header.

### [HIGH] `src/app/api/admin/subscriptions/route.ts:63-66` — Full table scan into memory for search
```js
if (search) {
  const q = search.toLowerCase();
  rows = rows.filter(r => r.business_name.toLowerCase().includes(q) || r.owner_email.toLowerCase().includes(q));
}
```
When `search` is provided, **no `.range()` is applied** (line 38 only adds range when not searching). The query fetches ALL subscriptions matching plan/status (potentially thousands) into Node.js then filters in JS. Also: `getUserEmailsByIds` issues one `auth.admin.getUserById` call per unique owner in the page — up to 25 separate auth API calls.
- **Proposed fix:** Pass search to a DB-side filter via an RPC or use a trigram index on `businesses.name` with a joined query. Cache email lookups.

### [HIGH] `src/app/api/admin/invoices/route.ts:28-33` — Full table fetch when searching
```js
let query = db
  .from('invoices')
  .select(`...`, withSearch ? undefined : { count: 'exact' })
  ...
if (!withSearch) query = query.range(offset, offset + PAGE_SIZE - 1);
```
When `withSearch` is true, **`count: 'exact'` is omitted AND `.range()` is not applied** — fetches all invoices (no pagination). For large invoice tables, all rows are loaded into memory then sliced in JS (line 48: `rows.slice(offset, offset + PAGE_SIZE)`). The search itself filters by `business_name` which requires loading the full join.
- **Proposed fix:** Use a trigram index on `businesses.name` + push search into the DB query with `.ilike()` on the joined column, or an RPC; apply `.range()` always.

### [HIGH] `src/app/api/analytics/summary/route.ts:32-37` — All copy events loaded just for meta tally
```js
db.from('analytics_events')
  .select('meta')
  .eq('business_id', businessId)
  .eq('event_type', 'copy')
  .gte('created_at', since)
// no .limit()
```
Fetches every copy event's `meta` JSONB column into Node.js to tally `draft_index` (lines 48–53). A business with 10k copies over 30 days loads 10k JSONB rows. The RPC `analytics_summary` already runs in the DB; this should too.
- **Proposed fix:** Add a DB function `count_draft_copies_by_index(p_business_id, since_ts)` returning `{first, second}`. Or query: `SELECT meta->>'draft_index' as idx, COUNT(*) FROM analytics_events WHERE ...`.

### [HIGH] `src/app/api/admin/plans/route.ts:17` — Fetches all businesses for client-side plan count
```js
db.from('businesses').select('plan'),
```
Loads **every business record** (just the `plan` column) into Node.js to do a JS-side GROUP BY (lines 22–25). Should be `SELECT plan, COUNT(*) GROUP BY plan` in the DB.
- **Proposed fix:** Use RPC or raw query: `db.from('businesses').select('plan, count(*)', { count: 'planned' }).` Or a simpler group-by RPC.

### [HIGH] `src/app/api/cron/gbp-sync/route.ts:36,45-117` — Unbounded fetch + sequential N+1 inserts
```js
const { data: connections } = await db
  .from('gbp_connections')
  .select('id, business_id, google_account_id, location_id, refresh_token')
  .eq('status', 'active');   // no .limit()

for (const conn of rows) {
  // ...fetches access token per-connection sequentially
  for (const review of page.reviews ?? []) {
    await db.from('gbp_reviews').insert({ ... });  // N+1 insert
  }
}
```
Three issues: (1) no limit on active connections fetched — large installs process thousands of connections in one cron run; (2) connections processed **sequentially**, not in parallel batches; (3) one `INSERT` per review inside the loop — should bulk-insert.
- **Proposed fix:** Add `.limit(100)` + cursor/offset for batched cron runs. Process N connections concurrently with `Promise.all` in chunks of 5–10. Use `db.from('gbp_reviews').insert([...reviews])` for bulk insert.

### [MED] `src/app/api/admin/businesses/[id]/route.ts:35-47` — Sequential awaits that could be parallel
```js
const { data: authUser } = await db.auth.admin.getUserById(business.owner_id);  // line 35
// ...
const { data: scanRows } = await db.rpc('admin_scan_counts_by_qr', { qr_ids: qrIds }); // line 41-42
// ...
```

The `getUserById`, `admin_scan_counts_by_qr`, `scans30d` count, and `auditLogs` fetch are all independent after the initial business query, but three run sequentially. Each adds one extra round-trip latency.
- **Proposed fix:** After fetching the business (needed for `qrIds` and `owner_id`), run all four in `Promise.all`.

## 2. Supabase / Database

### [HIGH] `database/001_initial_schema.sql:272-290` — RLS policies with subquery-per-row joins
The following RLS policies execute a subquery for **every row evaluated**:
```sql
-- qr_scans_owner_read — double join per row
qr_id IN (
  SELECT q.id FROM qr_codes q
  JOIN businesses b ON b.id = q.business_id
  WHERE b.owner_id = auth.uid()
)

-- reviews_owner_read — same double join per row
qr_id IN (
  SELECT q.id FROM qr_codes q
  JOIN businesses b ON b.id = q.business_id
  WHERE b.owner_id = auth.uid()
)
```
These affect all user-facing reads on `qr_scans` and `generated_reviews` (non-admin routes that use `createClient()`). Each row evaluation fires an uncached subquery.
- **Proposed fix:** Convert to `EXISTS` with indexed lookups, or add a `business_id` denorm column to `qr_scans` (already done on `generated_reviews` in migration 002) and use a direct equality check.

---

### [HIGH] `database/001_initial_schema.sql` — Missing index on `invoices (status)` and `invoices (created_at DESC)`
Admin invoices route filters by `status` (line 32 of invoices route) and always orders by `created_at DESC`. Only `invoices_business_idx` exists.
- **Proposed fix (SQL):**
```sql
CREATE INDEX IF NOT EXISTS invoices_status_idx ON public.invoices(status);
CREATE INDEX IF NOT EXISTS invoices_created_idx ON public.invoices(created_at DESC);
```

---

### [MED] `database/038_gbp_schema.sql:61-63` — Missing composite index on `gbp_reviews (connection_id, reply_status)`
Cron sync and reply queries filter by both columns. Two single-column indexes exist but no composite.
- **Proposed fix (SQL):**
```sql
CREATE INDEX IF NOT EXISTS gbp_reviews_conn_status_idx
  ON public.gbp_reviews(connection_id, reply_status);
```

```sql
CREATE INDEX IF NOT EXISTS review_reply_drafts_biz_created_idx
```

### [MED] `database/001_initial_schema.sql:283-290` — `analytics_owner_read` RLS subquery per row
```sql
CREATE POLICY "analytics_owner_read" ON analytics_events
  FOR SELECT USING (
    business_id IN (SELECT id FROM businesses WHERE owner_id = auth.uid())
  );
```
This subquery runs per row on a potentially large table. Since `business_id` is indexed and `businesses.owner_id` is indexed, it's mitigated but not eliminated.
- **Proposed fix:** Rewrite as `EXISTS`: `EXISTS (SELECT 1 FROM businesses WHERE id = analytics_events.business_id AND owner_id = auth.uid())`.

### [LOW] `{ count: 'exact' }` on large tables in admin stats
`analytics_events` can have millions of rows. `{ count: 'exact' }` with date filters relies on index-only scans; if the index is partial or not covering, it degrades to a seq scan. Current indexes on `analytics_events` cover `(business_id, event_type, created_at)` — for admin global queries with only `event_type` + `created_at`, confirm `idx_ae_business_type_time` is used or add:
```sql
CREATE INDEX IF NOT EXISTS ae_type_created_idx ON public.analytics_events(event_type, created_at DESC);
```

## 3. Admin Panel (Client)

### [MED] `src/app/admin/analytics/page.tsx` and `src/app/admin/subscriptions/page.tsx` — Raw `useEffect` fetch instead of React Query
Dashboard page uses React Query with `staleTime: 60_000` (correct). But analytics and subscriptions pages use raw `useEffect` + `fetch` with no caching, deduplication, or background refresh. Navigating away and back re-fetches every time.
- **Proposed fix:** Migrate to `useQuery` from `@tanstack/react-query` (already installed) with `staleTime: 60_000`.

---

### [MED] `src/app/admin/dashboard/page.tsx:36-52` — `dateRange` state doesn't affect API call
```js
const [dateRange, setDateRange] = useState('30d');

useQuery({ queryKey: ['admin-stats', dateRange], queryFn: () => adminFetch('/api/admin/stats') });
```
`dateRange` is in the query key (causing re-fetch on change), but the API URL `/api/admin/stats` is hardcoded and **doesn't receive the `dateRange` param**. The API always computes fixed 7d/14d windows. The toggle button re-fetches but returns identical data for 7d/30d/90d.
- **Impact:** Extra unnecessary re-fetches when switching date range tabs.
- **Proposed fix:** Either pass `?days=7/30/90` to the API and use it, or remove the `dateRange` from the query key.

---

### [MED] `src/app/admin/businesses/page.tsx` — No debounce on search input (line 161)
```jsx
onChange={e => { setSearch(e.target.value); setPage(1); }}
```
Every keystroke triggers a new API fetch. For slow connections or slow queries, this fires 5–10 requests per search.
- **Proposed fix:** Add `useDebounce` with 300ms delay before the search triggers.

---

### [LOW] `src/app/admin/_components/tables/data-table.tsx` — No virtualization
All rendered rows are in the DOM. With 25 rows this is fine, but if page size grows, consider `react-virtual` or `@tanstack/react-virtual`.

---

### [LOW] Charts loaded with `dynamic()` + `ssr: false` — already good
Dashboard uses `dynamic()` for Line/Donut/Funnel charts — correct for recharts. No issue here.

## 4. Caching / Revalidation Gaps

| Route | Current Cache | Recommended |
|---|---|---|
| `GET /api/admin/stats` | ❌ None | `s-maxage=30, stale-while-revalidate=60` |
| `GET /api/admin/stats/charts` | ❌ None | `s-maxage=60, stale-while-revalidate=300` |
| `GET /api/admin/analytics` | ❌ None | `s-maxage=60, stale-while-revalidate=300` |
| `GET /api/admin/businesses` | ❌ None | Not safe (filtered/paginated) |
| `GET /api/admin/subscriptions` | ❌ None | Not safe (filtered/paginated) |
| `GET /api/dashboard/overview` | ✅ `s-maxage=30, swr=60` | OK |
| `GET /api/analytics/summary` | ✅ `s-maxage=60, swr=300` | OK |

The three admin aggregate routes (`/stats`, `/stats/charts`, `/analytics`) compute expensive counts on every load. Adding `Cache-Control` headers makes Vercel Edge cache the response and serve subsequent requests instantly.
